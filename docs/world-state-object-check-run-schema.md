# World State: объект, проверка и запуск проверки

## Общая идея

Предметная модель состоит из трёх таблиц:

```text
world_state_objects
        │ 1
        ▼ N
world_state_checks
        │ 1
        ▼ N
world_state_check_runs
```

- Объект описывает, что именно проверяется.
- Проверка описывает, какое свойство безопасности исследуется у объекта.
- Запуск проверки хранит конкретные условия выполнения, результат и доказательства.

Для одного объекта создаётся одна проверка каждого вида. Например, у HTTP-параметра
`q` может быть одна проверка `xss` и одна проверка `sqli`. Разные payload, роли,
кодировки и прочие условия становятся отдельными запусками соответствующей
проверки.

## `world_state_objects`

Хранит хост, endpoint, HTTP-параметр или другой проверяемый объект.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `BIGINT`, PK | Идентификатор объекта |
| `flow_id` | `BIGINT`, FK → `flows.id` | Flow, которому принадлежит объект |
| `object_key` | `TEXT` | Стабильный канонический ключ объекта внутри flow |
| `type` | `TEXT` | Тип объекта: `host`, `endpoint`, `parameter` и т. п. |
| `locator` | `JSONB` | Структурированное описание местоположения объекта |
| `created_at` | `TIMESTAMPTZ` | Время обнаружения объекта |
| `updated_at` | `TIMESTAMPTZ` | Время последнего изменения описания |

Ограничение идентичности:

```sql
UNIQUE (flow_id, object_key)
```

Пример объекта:

```json
{
  "object_key": "parameter:GET:https://site/search?q=:query:q",
  "type": "parameter",
  "locator": {
    "url": "https://site/search?q=",
    "method": "GET",
    "location": "query",
    "name": "q"
  }
}
```

`locator` отвечает только на вопрос, где находится объект. Статусы, результаты
проверок и доказательства в нём не хранятся.

Для `host`, `endpoint` и `parameter` ключ вычисляет backend: достаточно передать
`type` и `locator`. Указанный вручную ключ должен совпадать с каноническим.
Учитываются схема URL, порт, HTTP-метод, location и имя параметра. У query-параметра
из идентичности исключается только его собственное значение; остальные query-условия
сохраняются. Например, `q=A&action=search` и `q=B&action=search` относятся к одному
параметру `q`, а `action=delete` — к другому контексту. Если метод неизвестен,
автоматическое обнаружение записывает `UNSPECIFIED`, а не предполагает `GET`.

## `world_state_checks`

Хранит вид проверки, выполняемой для объекта.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `BIGINT`, PK | Идентификатор проверки |
| `object_id` | `BIGINT`, FK → `world_state_objects.id` | Проверяемый объект |
| `kind` | `TEXT` | Вид проверки: `xss`, `sqli`, `ssrf`, `idor` и т. п. |
| `created_at` | `TIMESTAMPTZ` | Время создания проверки |
| `updated_at` | `TIMESTAMPTZ` | Время создания или изменения последнего запуска |

Ограничение идентичности:

```sql
UNIQUE (object_id, kind)
```

Статус проверки в этой таблице не хранится. Backend вычисляет его по актуальным
запускам, поэтому сохранённый статус не может разойтись с первичными результатами.

## `world_state_check_runs`

Хранит каждое фактическое выполнение проверки.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `BIGINT`, PK | Идентификатор запуска |
| `check_id` | `BIGINT`, FK → `world_state_checks.id` | Проверка, к которой относится запуск |
| `tool_call_id` | `BIGINT`, FK → `toolcalls.id`, NULL | Вызов инструмента, выполнивший проверку |
| `request_key` | `TEXT`, NULL, UNIQUE | Внутренний ключ повторного сохранения; в публичный DTO не входит |
| `parameters` | `JSONB` | Конкретные условия запуска |
| `execution_status` | `TEXT` | `planned`, `running`, `completed`, `failed` или `cancelled` |
| `verdict` | `TEXT`, NULL | `vulnerable`, `not_reproduced` или `inconclusive` |
| `evidence` | `JSONB` | Структурированные наблюдения и доказательства результата |
| `created_at` | `TIMESTAMPTZ` | Время создания запуска |
| `started_at` | `TIMESTAMPTZ`, NULL | Время начала выполнения |
| `finished_at` | `TIMESTAMPTZ`, NULL | Время завершения выполнения |

Один вызов terminal может выполнить несколько экспериментов, поэтому
`tool_call_id` не уникален. Технические дубли предотвращает:

```sql
UNIQUE (request_key)
```

Пример условий запуска:

```json
{
  "payload": "\"><svg onload=alert(1)>",
  "auth_role": "anonymous",
  "encoding": "raw",
  "injection_context": "html_attribute",
  "target_revision": "abc123"
}
```

Пример доказательств:

```json
{
  "response_status": 200,
  "response_excerpt": "value=\"\"><svg onload=alert(1)>\"",
  "reflection_context": "html_attribute",
  "script_executed": true
}
```

Перед сохранением backend маскирует распознаваемые cookies, токены, пароли,
заголовки авторизации и секреты в URL в `locator`, `parameters` и `evidence`.
Произвольный текст всё равно следует передавать без секретов: автоматическое
маскирование не определяет семантику любого значения. Для сессий используйте
ссылку/роль, а не сырые credentials.

Полностью одинаковые фактические запуски сохраняются отдельными строками. Это
позволяет видеть воспроизводимость результата. Повторная запись результата одного
и той же операции `start_run` возвращает существующую строку благодаря
`request_key`. Executor формирует ключ из flow, task/subtask, цепочки и ID
логического вызова; агент этот ключ не придумывает. Повтор `finish_run` с теми же
данными также идемпотентен. Итог завершённого запуска изменить нельзя: новое
наблюдение сохраняется новым запуском.

## Вычисление статусов

У запуска отдельно хранятся состояние выполнения и итог проверки:

- `execution_status` показывает, было ли выполнение завершено;
- `verdict` показывает, что установлено в результате выполнения.

Статус проверки вычисляется по всем сохранённым запускам, в порядке приоритета:

- есть подтверждённый `vulnerable` → `vulnerable`;
- есть незавершённые запуски → `in_progress`;
- есть failed или completed/inconclusive → `inconclusive`;
- завершённые варианты имеют только `not_reproduced` → `not_confirmed`;
- полезных результатов нет (в том числе только cancelled) → `unknown`.

Отрицательный результат с другим payload или другими условиями не отменяет
подтверждённую уязвимость. `target_revision` из `parameters` помогает сравнивать
условия, но сам по себе не снимает исторический положительный результат.
Автоматическое определение «исправлено» в эту версию не входит.

Статус объекта также вычисляется: если хотя бы одна его актуальная проверка имеет
статус `vulnerable`, объект считается уязвимым.

## Пример структуры

```text
Объект: параметр q в GET /search
│
├─ Проверка: XSS
│  ├─ payload A, гость       → vulnerable
│  ├─ payload B, гость       → not_reproduced
│  └─ payload A, авторизация → not_reproduced
│
└─ Проверка: SQL injection
   ├─ boolean payload → not_reproduced
   └─ time payload    → inconclusive
```

При обращении агента backend собирает из таблиц структурированное представление:

```json
{
  "object": {},
  "checks": [
    {
      "kind": "xss",
      "computed_status": "vulnerable",
      "runs": []
    }
  ]
}
```

В реализации это Go DTO `ModelSnapshot` с `schema_version`, `flow_id`, `revision`,
счётчиками и массивом `objects`, внутри которого находятся `checks` и `runs`.
API и интерфейс используют эту структуру напрямую.

Перед каждым обращением к LLM в цикле агента `callWithRetries` строит свежий
`ModelContext` из согласованного снимка БД. Перед провайдером структура
сериализуется в JSON с `kind: world_state_snapshot` в копии массива сообщений.
Отдельно в начало запроса добавляется постоянный системный протокол чтения
World State: что означают object/check/run, `parameters`, `evidence`, статусы,
ревизия, счётчики и пропуски; что возвращают `world_state_query` и
`world_state_update` и как пользоваться их результатами. Протокол дописывается
в существующее первое system-сообщение, а при его отсутствии создаётся первым.
Он добавляется заново на каждом запросе, в том числе после суммаризации и при
повторной попытке обращения к модели.

Статические инструкции не зависят от содержимого таблиц. Снимок содержит только
типизированные данные (`ModelContext`); поле `usage` из JSON удалено. Сами
`locator`, `parameters` и `evidence` передаются отдельным блоком данных и не
попадают в системные инструкции. Пояснение схемы и снимок существуют отдельно
вплоть до сборки сообщений для провайдера.

Сам LLM API по-прежнему принимает сообщения/текст, но код до этой границы работает
с типизированными объектами, а не разбирает XML-теги. Снимок не добавляется в
сохраняемую/суммаризируемую историю, включая шаблоны generator/refiner.
Если актуальный снимок прочитать не удалось, запрос агента не отправляется.

Контекст ограничен 64 КиБ, до 32 объектов, 16 checks на объект и 8 runs на check;
при превышении размера детали дополнительно сокращаются. Полные счётчики и
статусы не меняются, пропуски явно указаны в `omitted`. Детали доступны через
`world_state_query` с фильтрами `object_id`, `check_id`, `kind`, `type`, `state`
и пагинацией `object_limit/object_offset`, `run_limit/run_offset`.

После успешного ответа primary-агента курсор продвигается только до ревизии,
включённой в этот запрос. События, пришедшие во время ответа LLM, остаются
недоставленными и могут разбудить ожидающего агента. Такое пробуждение означает
пересмотр ситуации; оно не является ответом или согласием пользователя.

Технические таблицы журнала событий и курсоров доставки могут существовать
отдельно. Они не входят в предметную модель «объект → проверка → запуск».

## Запись и совместимость

Агент заполняет проверки и результаты явными операциями `world_state_update`:

1. `observe_object`: `type`, `locator` → `object_id`.
2. `ensure_check`: `object_id`, `kind` → `check_id`.
3. `start_run`: `check_id`, `parameters` → `run_id`, состояние `running`.
4. `finish_run`: `run_id`, `execution_status`, `verdict`, `evidence`.

Для `completed` нужен verdict; для `failed/cancelled` он отсутствует, а причина
идёт в evidence. Состояние `planned` поддерживается слоем хранения для иных
потребителей; инструмент агента начинает запуск непосредственно перед проверкой.

Автоматический обработчик вывода инструментов только обнаруживает конкретные
hosts/endpoints/parameters. Он не создаёт подтверждённых уязвимостей, checks или
runs по словам `XSS`, `SQLi` и т. п. Все изменения фиксируются вместе с событием
в одной транзакции; повтор записи без изменения данных нового события не создаёт.

Миграция `20260910_120000_world_state_object_checks.sql` добавляет
`flows.world_state_schema_version`: существующие flow остаются на версии 1,
новые создаются с версией 2. Старые entities/transitions/links сохранены и
доступны через прежние инструменты и интерфейс. Автоматически превратить старый
общий статус в доказанный run нельзя, поэтому вымышленные исторические запуски
не создаются.

Новый endpoint `GET /flows/:flowID/worldstate/model` отдаёт текущую структуру
с проверкой прав на flow. Для старого flow он явно сообщает `schema_version: 1`;
UI выбирает legacy-представление только по версии, а не по сетевой ошибке.

Сейчас snapshot/API загружают полный flow; пагинация инструмента применяется
после вычисления статусов. Это сохраняет корректность агрегатов, но для очень
больших flow потребуется отдельная оптимизация запросов и API-пагинации.

Эта модель хранит наблюдения, действия и результаты. Обучаемый предиктор будущих
состояний или симулятор действий из обсуждённой статьи здесь не реализуется.

## Проверка реализации

Проверки выполнены в отдельных Go/Node/PostgreSQL-контейнерах, без миграции
рабочей БД и без перезапуска текущего сервиса:

- Backend собирается командой `go build ./...`.
- PostgreSQL-тесты проверяют миграцию вверх/вниз/вверх, сохранение старых flow,
  конкурентную запись, идемпотентность, изоляцию flow и откат записи вместе с событием.
- Тесты реального обработчика инструментов проверяют полный цикл объекта/check/run,
  отрицательные варианты, пагинацию, evidence и точное сохранение больших числовых ID.
- Тесты provider проверяют наличие системного протокола на каждом запросе,
  сохранение прежних system-инструкций и tool-цепочек, отсутствие данных цели
  в system, свежие снимки и отсутствие их в сохранённой истории,
  восстановление после суммаризации, курсор конкретной доставленной ревизии и
  запрет подтверждать доставку другому flow.
- Прошли сборки обоих интерфейсов и TypeScript-проверка frontend. Три UI-теста
  проверяют сохранение отдельных runs, показ отрицательных вариантов и экранирование evidence.

При общем прогоне найден существующий сбой
`attackplan.TestStoreConcurrencyRollbackReplayAndBinding` (`terminal reopen error = <nil>`).
Он отдельно воспроизведён на неизменённом `a041ff9`, без новой миграции:
`TransitionNode` меняет общий срез узлов до сравнения старого и нового графа.
Поведение attackplan в рамках этой замены не исправлялось. Остальные тесты
миграций, контроллера, API и attackplan прошли с явным исключением этого теста.

Перед публикацией ветки 11 сентября 2026 выполнена сборка production-образа
штатным `Dockerfile` из точного набора файлов будущего коммита. Образ запущен
с отдельной пустой PostgreSQL на `127.0.0.1:18443`; рабочая установка не менялась.
Все 12 HTTP-проверок прошли: запуск и встроенный frontend, реальный вход,
модель v2 и пустая модель, совместимость v1, запрет анонимного доступа,
изоляция чужого flow, обработка неверного/отсутствующего ID, чтение после
перезапуска приложения. Snapshot до и после перезапуска совпал полностью.
В браузере проверены вкладка World State, отдельные положительный и
отрицательный runs одной проверки, раскрытие parameters/evidence и вывод
HTML-фрагментов как текста. Тестовые данные записывались через production
`ModelStore`; внешний LLM и worker сканирования в этой проверке не запускались.

Финальный обзор также выявил и устранил попадание распознанных credentials
из URL path в `object_key`: такой locator теперь отклоняется до записи.
Регрессионные тесты проверяют обычный и percent-encoded path, отсутствие
секрета в ошибке и сохранение допустимого маршрута `/password-reset`.
